# 截屏翻译 V2：原位替换与实时区域翻译

2026-10-02。状态：设计 + 离线原型。原型在 `scripts/screen-eval/v2/`，不编进应用，`Sources/` 没有改动。文中数字都来自本机（M3 Max，macOS 26.7）在 24 张样例上的实测，标"目标"的是验收门槛。实时区域翻译只有设计，没有原型。

对比图：`build/screen-eval/gallery.html`（全部样例四联图），`build/screen-eval/highlights/`（几张拼好的长图）。

## 1. 要达到的效果

像把系统语言从中文切到英文：每段文字还在原来的位置，字号、粗细、颜色、对齐都没变，背景、图标、图片一个像素不动，只是文字换了语言。没有贴片、模糊、圆角条，块里不滚动。

第二个能力：框住一块区域后持续翻译，区域里出现文字就自动翻（视频字幕、聊天窗口、游戏界面）。

## 2. 真实的"切语言"长什么样

历史文档里的描述不作数，这次直接抓了同一页面由发布方自己做的中、英文版，连同页面自己知道的真值（每段文字的矩形、字号、字重、颜色、字体）：Apple 支持页、GitHub Docs、MDN、Vue 文档，再加一张自建的应用界面用例（侧栏、工具栏、聊天气泡、设置项、卡片、表格、视频字幕，深浅两套）。每张都有 1x 和 2x。

看到的事实：

1. **字号、字重逐元素完全相同。** Apple 那一页 28 个对应元素，中英文的字号和字重 28 个全等（12/12、17/17、24/24、40/40），只有字体随文字换（SF Pro Text → SF Pro SC）。左对齐块的左边缘也相同。
2. **中文只占英文 57%–67% 的宽度**（Apple 0.57，GitHub Docs 0.67，自建用例 0.64）。英译中总是放得下；中译英要 1.5–1.8 倍的宽度，这是难的方向。
3. **真实本地化会重排。** 中文段落从 4 行变 2 行，下面的内容整体上移；居中的导航栏重新分配间距。原位翻译不能推动别的内容，所以英译中会留白，中译英要有放不下时的策略。
4. **图片里的字，发布方自己不翻。** Apple 中文页里工具栏截图上的 "Capture" 还是英文。我们要翻，这是比真实本地化多做的一步。
5. **你的主显示器是 1x**（2560×1440）。13 号字只有 13 个像素高，测量和渲染都必须在 1x 下成立，不能只看 Retina。

## 3. 现有版本的得分

把现在出货的流水线原样编出来（`scripts/screen-eval/baseline.swift`，用的就是 `Sources/Screen` 的代码），在 24 张样例上跑，按真值打分：

| | 块数 | 字号误差中位 | p90 | 平均偏差 | 误差 ≤5% 的块 |
| --- | --- | --- | --- | --- | --- |
| 现有版本 | 848 | 17.4% | 33.7% | +18.3% | 3% |
| V2 原型 | 951 | 0.9% | 6.3% | +0.4% | 86% |
| V2 原型，2x | 476 | 0.3% | 4.6% | +0.3% | 91% |
| V2 原型，1x | 475 | 1.8% | 7.0% | +0.6% | 81% |

现有版本的字号系统性偏大近两成，这就是"圈出来以后字的大小和原来不一样"。原因在代码里很明确：字号由 OCR 行框的高和宽除以系统字体的比例得到（`ScreenTranslate.sourceFontSize`），而行框比真实墨迹高出一截，原文也不一定是系统字体。其余问题在对比图上一目了然：整段换成模糊贴片；白字变黑字、灰字变黑字；按钮和气泡里的字盖住容器；导航栏被并成一句话；图标被当成字擦掉。

V2 原型的颜色误差中位为 0（每通道），粗细判断在各样例上 81%–100% 正确。

## 4. 原则

1. OCR 只回答"写了什么、大概在哪"。字号、基线、粗细、颜色、对齐、背景一律从像素量出来。
2. 擦掉的是笔画，不是矩形。
3. 排版跟原文走：同字号、同行距、同基线、同对齐。放不下时按固定顺序退让。
4. 模型负责"理解"（整屏语境下的翻译、哪些是品牌名、译文压缩）；坐标和字号由测量给出，模型不生成几何。
5. 一条流水线，两种驱动：单帧（截屏）和连续帧（实时区域）。
6. 每一步都对着真值打分。构建通过不算验收。

## 5. 流水线

```
ScreenFrame ─► Recognize ─► Measure ─► Structure ─► Translate ─► Fit ─► Erase ─► Compose
  像素+比例      文字与行框    墨迹与样式   分段/对齐/空白    译文        排版    还原背景   一张译图
```

下面每一节先写做法，再写原型在真实样例上撞出来的修正。这些修正是设计的一部分。

### 5.1 Recognize（识别）

- Vision 逐行识别，不在这一步合并同一行的片段。两个片段是否属于一行，由它们之间的像素决定：中间只有同一种背景才合并。现有版本按间距盲合，会把相邻的两个标签、两个表头并成一个词组。
- 一行里背景换了颜色就拆开（并排的两个标签各有底色）；一句话里夹着一个高亮词不拆（大部分词落在行外的背景上）。
- 行首尾被扫进来的图标不算字：实心、颜色或高度和文字不同的一段留在原图里，对应的字符从文本里去掉。
- macOS 26 的 `RecognizeDocumentsRequest` 能给出段落、列表、表格（实测可用），正式实现时用它做分段的起点。原型为了和现有版本公平比较，用的是同一个识别请求。
- Vision 的语言顺序有坑：英文排第一时，纯中文行整行不出结果。

没解决的：下拉箭头被读成字母 "v"，导航栏 "HTML ∨ CSS ∨ JavaScript ∨" 被当成一句话。需要一个图标检测（规则或小模型）在识别前把图标挖掉。

### 5.2 Measure（测量）——核心

对每一行，在原始分辨率上：

1. **背景**：取行框边缘一圈的主色。按钮、标签里的字，背景是按钮的颜色，不是按钮外面的颜色。一圈颜色不一致时再判成渐变或图片。
2. **笔画**：每个像素相对背景的色差归一成覆盖度。字是背景里的"孤岛"：不是背景、又连到分析窗口边缘的区域（按钮外的页面、相邻的行、被切到的图标）不算这一行的墨迹。几乎整行都被填满的行是容器的边，不是字。
3. **图片上的字**（字幕、封面标题）：没有背景色可比，改成找"整行里保持不变的那种颜色"：框内像素分三簇，文字是最亮或最暗的一簇；白字黑边时两簇都像，取离中间簇远、且不贴着框边的那一簇。
4. **词**：墨迹按词间距切成段，每段有自己的顶、底、颜色、周围底色。字号取"典型的词升到基线以上多高"，一个图标或一个怪字形不会带偏整行。
5. **字号**：把同一串字用参考字体画出来、用同一套测量量一遍，比高度，迭代到一致。参考图的基线落在整像素上，和应用画字的方式一致。汉字每个字宽一个 em，与字体无关，所以中文行用宽度定字号。
6. **粗细**：在估出的字号下画常规到粗体几档，取笔画宽度和原文最接近的一档，同时判断原文是否开了系统的字体平滑。参考图用原文的字色和底色画，深色底上的浅字才比得准。
7. **颜色**：笔画中心像素的颜色，按覆盖度还原，1x 下的细笔画也能得到真实字色。
8. **字体类别**：只在证据明确时判等宽或衬线，否则按无衬线。等宽的不翻译（代码）。

同一种样式的行测出来会差一点。全屏把字号相近、颜色相同的块聚成组，组内统一字号：人眼最敏感的是"两段同级文字不一样大"。

### 5.3 Structure（结构）

- **是换行还是并列**：上一行之所以断开，是因为下一个词放不下。如果上一行右边的空白放得下下一行的第一个词，这两行就是并列的标签，不是一段。句子明显没说完（小写开头、逗号结尾）时仍算一段。
- 两行之间隔着一条贯穿的边，或各自被自己的容器紧紧包着（两个胶囊右边缘不同），就不是一段。
- 项目符号开头的行各自成段。
- **对齐**：多行块看各行的左、中、右哪条线最齐。单行看上下邻居在哪条线上对齐；没有邻居再看它在容器里的位置。
- **空白**：从块向四周扫描，直到遇到别的东西。纯色背景上按颜色判断，渐变和图片上按相邻像素的跳变判断。记录是被边界拦住还是到了截图边缘、上下拦住它的是不是一条贯穿的边（按钮、气泡、输入框），后者决定译文是垂直居中还是顶对齐。
- 不翻译：代码和标识符（`font-size`、`createApp({`）、等宽字体、纯数字、已是目标语言的行。一句完整的话里夹着符号仍然是话。

### 5.4 Translate（翻译）

原型只接了苹果本地翻译，逐块送。几何对了以后，剩下最刺眼的就是用词，样例里的真实错误：

| 原文 | 苹果翻译 | 应该是 |
| --- | --- | --- |
| Share（按钮） | 份额 | 共享 |
| Live（视频角标） | 过 | 直播 |
| Free（标签） | 未受困的 | 免费 |
| macOS 27 Golden Gate | macOS 27 金门 | 不译 |
| Watch / Vision（苹果导航） | 手表 / 视力 | 不译 |
| Slots（Vue 文档目录） | 老虎机 | 插槽 |
| 发送（按钮） | Transmission | Send |
| 赞助商的商标图 | 逐个译成中文 | 不译 |

这些都不是单句翻译能解决的，要整屏语境。所以保留两级：

- **快翻**：苹果本地翻译。离线，不用下载，现状。
- **精翻**：一次把整屏结构化送给语言模型：`[{id, role, text, max_chars}]` 加应用名和窗口标题，返回 `[{id, text 或 keep}]`。它负责术语、界面惯用词、品牌和商标保留，以及按 `max_chars` 给出更短的译文（中译英放不下时用）。后端是本机 MLX 模型或用户已配置的接口；本机用哪个模型要像语音那样先评测再定，候选的几个翻译模型在本项目里都还没测过。

### 5.5 Fit（排版）

按顺序，满足即停：

1. 原字号、原行距、原基线、原对齐，在原栏宽内。
2. 原字号，用像素证明过的空白：先加宽，再加行。加出来的行可以排得比原文紧，但不低于 1.2 倍字号。
3. 小一档字号（0.96、0.92 … 0.70），每一档重复 1、2。
4. 都放不下：停在 0.88 倍，用满能用的行数，末行截断加省略号。
5. 截断后几乎显示不出内容的，保留原文不动。

同一组同级的块（同样式、同一列或同一行）里多数需要缩小时，整组缩到同一档；只有个别需要时不拖累整组。紧贴容器的块（按钮、气泡、标签）译文在容器里居中，页面上的段落保持顶对齐。

实测：

| 方向 | 放置的块 | 缩小 | 截断 | 保留原文 |
| --- | --- | --- | --- | --- |
| 英 → 中 | 544 | 1 | 0 | 6 |
| 中 → 英 | 469 | 79（17%） | 28（6%） | 19 |

英译中基本原字号原位。中译英是受原位约束的：气泡、按钮是照着中文的宽度画的，英文放不进去。现在的做法是在容器里缩小并排成两行，内容完整但字变小。要更自然只有两条路，见第 9 节。

### 5.6 Erase（还原背景）

只动笔画蒙版（外扩 1–2 像素盖住抗锯齿边）覆盖的像素：纯色背景填背景色，结果与无字时一致；渐变和图片由蒙版外向内插值（金字塔 push-pull）；图片上的字外扩得更宽，把描边和阴影一起带走。照片这类复杂背景将来可换小型修复模型，接口不变。

### 5.7 Compose（合成）

一张与原图同尺寸的译图：原图 + 还原的背景 + Core Text 画的字。基线落在整像素；是否平滑跟原文；图片上的字加一圈反色的柔边保证可读。钉住面板只需要原图层和译图层两层，复制出去的就是这张图。现有的逐块视图、模糊底图、块内滚动都不再需要。

## 6. 原型没解决的

1. 图标被读成字母（下拉箭头 "v"），导航栏被当成一句话。
2. 商标和品牌图被翻译。靠精翻的 keep。
3. 中译英 17% 的块要缩小、6% 截断。
4. 字面占 em 比例特殊的字体会偏：Apple 网页的中文字体字面偏小，量出来比 CSS 字号小约 5%（视觉大小是对的）。1x 下不认识的西文字体有约 ±5% 的偏差，GitHub Docs 英文页 1x 整页偏大 5%，2x 下是 0.9%。
5. 两三个字的中文短标签在 1x 下粗细容易判错（中文样例粗细正确率 81%–88%）。
6. 衬线体识别弱，Georgia 这类会被当成无衬线渲染。
7. 段落内的局部样式会丢：蓝色链接、行内代码、加粗词，整段按一种样式重排。
8. 测量阶段太慢：1x 每屏约 3 秒，2x 约 8 秒（每行画了十来张参考图）。正式实现要改成按样式组而不是按行做参考比对，目标 0.2 秒以内。这是确定要做的工程量，不是已经达到的数字。
9. 样例全是网页和自建页面。原生应用窗口、微信/飞书这类聊天软件、游戏、真实视频帧还没进样例集，因为那需要截屏权限，你不在的时候没有做。5K 大图的分块识别、竖排和旋转文字原型里也没有。

## 7. 实时区域翻译（Live Lens）

只有设计，没有原型。单帧流水线原样复用，外面加三件东西：

```
SCStream(区域, 排除自己的窗口, ≤10 帧/秒)
   └► FrameGate   每帧，约 1 ms：已显示的块底下的原文还在吗？哪里出现了新内容？
        ├► 原文没变 → 译文保持不动
        ├► 原文变了 → 该块译文立刻隐藏（一帧之内）
        └► 有新内容 → 排队识别（同时只跑一个，合并请求）
             └► Measure → Structure → Translate(缓存) → Fit → LiveOverlay
```

1. **采集**：`SCStream` + `sourceRect`，过滤器排除本应用的窗口。采到的永远是译文层底下的原始像素，不会把自己的译文再识别一遍。画面不变时系统不送帧，空闲零开销。
2. **门控**：每个已显示的块存一份原文签名（笔画区域的低分辨率亮度），每帧比对，不一致立即隐藏。旧译文盖在新内容上的时间不超过一帧。
3. **识别节奏**：Vision 的 fast 级别在试过的一张网页截图上一行都没识别出来，不能指望；accurate 级别 1600×240 的条带约 0.3 秒，1600×806 约 0.8 秒。所以不是每帧识别：画面静止 150 ms 后识别一次；画面持续变化（视频）时约每 0.4 秒识别一次。
4. **文本级去抖**：识别结果和已跟踪的行按"文字 + 位置"匹配。同一句字幕在背景不停变化时每次都匹配上，不重翻、不闪。逐字出现的文字等稳定 400 ms 或到句末再翻。
5. **背景静止**（聊天、网页、游戏面板）：和截屏完全一样，擦字、原位排版。**背景运动**（视频）：静态补丁盖不住会动的画面，改为字幕条，正好盖住原字幕的深色半透明条加同字号白字。原型里字幕的测量和重排已经能做（见用例里的视频字幕），实时模式缺的是逐帧的背景。
6. **滚动**：签名全部失效，译文一帧内隐藏，停下后识别，缓存命中的块不重翻。译文跟着内容滚放到后续。
7. **叠加窗口**：盖住区域，鼠标穿透。区域边上一个小胶囊：暂停、方向、关闭、定格成截图。
8. **预期延迟**（由上面的实测推算）：字幕出现到译文出现 0.5–0.9 秒。

## 8. 评测工具

都在 `scripts/screen-eval/`，产物在 `build/screen-eval/`（不入库）。

```bash
bash scripts/screen-eval/build.sh                 # 编三个工具
scripts/screen-eval/capture.sh                    # 抓样例图和真值（联网抓四组真实页面）
scripts/screen-eval/run.sh baseline build/screen-eval/out   # 现有版本
scripts/screen-eval/run.sh v2 build/screen-eval/out         # V2 原型
python3 scripts/screen-eval/score.py build/screen-eval/pages build/screen-eval/out current
python3 scripts/screen-eval/score.py build/screen-eval/pages build/screen-eval/out v2
python3 scripts/screen-eval/gallery.py build/screen-eval/pages build/screen-eval/out build/screen-eval/gallery.html
```

- `snapshot.swift`：不显示窗口地渲染网页，导出截图和页面自己的真值。2x 图借用内建 Retina 屏的比例。
- `fixtures/app.html`：自建用例，`?lang=en|zh`、`&theme=dark`。
- `baseline.swift`：出货流水线，直接编 `Sources/Screen` 的源码。
- `v2/`：原型，约 1,900 行，值类型加纯函数，按阶段分文件，可以整体搬进 `Sources/Screen/Pipeline/`。
- `score.py`：只有文字读起来对得上的真值才算数；一行里混着几种字号的不计分。

验收目标：字号误差中位 ≤3%、p95 ≤6%（1x 和 2x 分别满足）；同样式块字号相同；纯色背景还原零误差；截屏首次出图 ≤1.5 秒；实时模式出现 ≤1 秒、残留 ≤150 ms、稳定文字零闪动。

## 9. 需要你定的

1. **中译英放不下时**：现在是"容器里缩小并换行，再不行截断"。看 `build/screen-eval/highlights/app-zh-en.png` 里的气泡和按钮。另外两条路：
   - 让精翻给更短的译文（"New Message" 而不是 "New information"）。便宜，建议做。
   - 把容器一起拉大（气泡、按钮、标签是纯色圆角矩形，可以九宫格拉伸）。效果最接近真实本地化，但会盖到旁边的内容，工作量大，建议放后面。
2. **精翻后端**：只用本机模型，还是同时保留自定义接口。建议本机为默认，保留自定义接口。
3. **视频字幕**：接受字幕条样式，还是投入做逐帧修复。建议先字幕条。
